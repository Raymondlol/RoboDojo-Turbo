# Patches and switches

Every switch is an environment variable read by the patched RoboDojo code; unset means upstream behaviour. Check modes
(counters, cumulative over the process, printed after every batch as `[robodojo-turbo] batch-stats ...`) differ in which
result the run continues with:
`CTRL_CACHE`, `PARENT_CACHE`, `PCI_COPY` and `BATCH_TENSOR` compute both paths and continue with the upstream result;
`VIDEO_ONLY_OBS` (incl. `RGB3`) compares both and continues with the fast path's frames; `USD_LAST=check`
keeps the fast path and compares the USD pose with the PhysX pose after every action (there is no upstream path to run;
`basecheck` does the same comparison with the switch off). `REVOKE_LISTENERS`, `GC` and `VIDEO_MV` have no check mode.
Values outside a switch's documented set mean upstream behaviour (`check-env` reports them). Measurements below were taken with the private predecessor of
this code on one RTX 5090 + Ryzen 9 9950X3D, `stack_blocks`, 1 process x 10 envs, official pi0.5 checkpoint, unless noted.

## Harness (`--profile harness`)

| patch | switches | what it does |
|---|---|---|
| trace | `RDTURBO_TRACE=<path.jsonl>`, `RDTURBO_WORKER` | span tracer on EvalEnv and the websocket client; input to the bubble report and `tools.batch_times` |
| layout_shards | `RDTURBO_LAYOUT_IDS`, `RDTURBO_NUM_ENVS`, `RDTURBO_EVAL_NUM_FORCE=1` | evaluate a subset of layouts per process; override `num_envs`; lift the per-task `eval_nums` cap that silently truncates larger shards |
| pi05_loop | `RDTURBO_OBS_EVERY_STEP=0`, `RDTURBO_VIDEO_EVERY` (keep 1: see below), `RDTURBO_RECORD_ACTIONS`, `RDTURBO_REPLAY_ACTIONS`, `RDTURBO_REPLAY_STRICT`, `RDTURBO_STATE_TRACE`, `RDTURBO_PARTICLE_TRACE`, `RDTURBO_OBS_DUMP` | replaces XPolicyLab's Pi_05 batch loop. Defaults reproduce the upstream call sequence exactly (tested against the upstream function). `OBS_EVERY_STEP=0`: between chunk starts, observations are rendered for the video only and not uploaded; the Pi_05 server overwrites its observation window on every upload and reads it only at `get_action_batch`. `VIDEO_EVERY=k>1` renders only every k-th in-chunk step (video fps divided by k) and `0` renders chunk starts only (fps not adjusted): **both change the protocol**, because RTX anti-aliasing is temporal and the chunk-start image the policy sees depends on the frames rendered before it (the predecessor saw 1/25 vs 3/25 successes at k=5, n = 25, not significant); keep 1 for comparable scores. The other switches are verification tooling (record/replay action chunks, float64 state traces incl. articulated objects, the USD points fluid/garment scorers read, chunk-start camera images) |
| fast | `RDTURBO_FAST=1`, `RDTURBO_VIDEO_CAMS` | lossless copy/recompute removal: whole-tensor clones and deepcopies whose results are copied again downstream (B1/B6), controls resolved twice per pop (B1), back-to-origin predicates computing every env to use one (B3), observation deepcopy replaced by an array-copying walk (B2), per-step prints (B8), x264 `ultrafast` (B5; file size only); the labels B1-B8 are the ones used in the injected comments. `VIDEO_CAMS=cam_head` records one camera. Measured together: FAST=1 + head-camera video vs FAST=0 + three cameras, 1.20x per GPU on 4x RTX 4090 (RoboDojo ee67a14, before upstream changed `get_obs_batch` on 2026-09-12), 100 layouts paired score difference -1.7 [-8.2, +4.6] vs +4.3 between two FAST=0 runs on different machines |
| ffmpeg_threads | `RDTURBO_FFMPEG_THREADS=<n>` | caps x264 threads per video stream (x264 defaults to 1.5x visible cores per stream; 4 workers x 30 streams on a 64-core container with pids.max 5120 failed with BrokenPipe). The presets set 2, as in the measured runs |
| accounting | `RDTURBO_STATUS`, `RDTURBO_STRICT=1` | RoboDojo's main loop catches generic exceptions, consumes the failing batch's seeds and exits 0. This counts such batches, writes a status file, and with `STRICT=1` exits with status 4 |

## Speedup switches (`--profile speedup`)

| switch | mechanism | evidence (predecessor code) | scope / caveats | prior art |
|---|---|---|---|---|
| `RDTURBO_REVOKE_LISTENERS=1` | RoboDojo launches the full GUI experience file even headless, so five UI extensions register Python `Usd.Notice.ObjectsChanged` listeners that fire on every per-substep pose write-back. Revoke them in process and intercept re-registration (the stage is re-opened every batch) | py-spy: 14.2% of main-thread time; physics 154 -> 115 ms per step (-14.5% per batch). No listener reader exists headless (read of all five callbacks and their consumers) | covered by the 2026-09-27 replay with every switch off vs the speedup preset (docs/validation.md) | IsaacSim #819 profiles listener costs; OmniGibson revokes one of the five (UsdWatcher) for teardown correctness |
| `RDTURBO_RGB3=1` | the tiled-reshape kernel writes 3 channels instead of RGBA for the rgb annotator | byte-equal to upstream `[..., :3]` in check mode | restores upstream Isaac Sim `CameraView` behaviour that RoboDojo's fork changed | Isaac Sim `camera_view.py`; Isaac Lab switched to (H, W, 3) in 2024 |
| `RDTURBO_VIDEO_ONLY_OBS=1\|check` | on steps whose observation only feeds the video, render as before but read out only the recorded cameras and skip assembling the observation | check: 539 calls / 5,059 frames byte-identical; obs 115 -> 80 ms per step (with RGB3) | Pi_05 loop with `OBS_EVERY_STEP=0` only. Check mode reads all cameras, so it does not exercise the `=1` wrist-camera skip; the chunk-start frame comparison (`RDTURBO_OBS_DUMP`, 2026-09-27) found `=1` vs `=0` within render noise on all three cameras (docs/validation.md) | none found for the mechanism; RLinf skips rendering (not allowed here) |
| `RDTURBO_USD_LAST=1\|check\|basecheck` + `RDTURBO_USD_LAST_MODE` | stop per-substep PhysX -> USD write-back inside an episode. `flush`: `update_transformations` once per action (rigid bodies and links only). `last`: restore write-back for the last substep of each action (everything, incl. particles and cloth). `keep-particles`: `flush` with particle write-back kept on (fixes fluids, not cloth; experiments only). `auto` (default): `last` on fluid/garment scenes, `flush` otherwise | physics 115 -> 57 ms per step; replay bit-identical 5,164/5,164 on `stack_blocks`. Fluid/garment: `flush` froze particles/cloth in USD and scored 0/10 on both tasks; `last` restores scores to the noise band (docs/validation.md) | Pi_05 loop only. Kit 107 (Isaac Sim 5.1) semantics. Not applied during reset (teleported bodies that fall asleep would keep stale USD poses). **Bodies that fall asleep during an action stay stale in USD (neither `flush` nor `last` writes them): up to 1.2 mm and ~6 deg on 5 of 11 tasks checked 2026-09-27, none on `stack_blocks`. Physics unchanged and scores identical in a 10-layout replay A/B on the laptop task (whose scorer reads USD; 1/10 successes in every arm); see docs/validation.md** | NVIDIA forum 164502 (2023), Isaac Lab's Fabric render-time flush, IsaacLab PR #7642; IsaacSim #819 |
| `RDTURBO_GC=freeze[,log]` | `gc.freeze()` after start-up and after every batch reset; unfreeze before reset/close | start-up to first reset: 38 full collections / 11.6 s -> 0.75 s; nothing in-episode once listeners are revoked | | CPython `gc.freeze` (Instagram) |
| `RDTURBO_CTRL_CACHE=1\|check` | `control_robot` re-resolves a control that `pop()` resolved in the same substep; reuse it (gripper clamp is idempotent). Guarded: only when the recorded substep counter exists and matches | check: 105,540 float32 comparisons, 0 mismatches | franka support-arm branch checked 2026-09-27 (3 tasks, 0 mismatches) | generic |
| `RDTURBO_PARENT_CACHE=1\|check` | read a rigid object's static parent Xform world matrix from USD once per physics view | check: 5,164 comparisons, 0 mismatches | parents are static category Xforms in every task (static audit) | NVIDIA staff advice on USD-backed `get_local_poses` |
| `RDTURBO_VIDEO_MV=1` | write frames to ffmpeg via `memoryview` (no `tobytes()` copy); 1 MiB pipe when running as root (an unprivileged user's pipes share a 64 MiB budget, and exceeding it shrinks every new pipe of that user to 8 KiB) | equivalent by construction: the frame is C-contiguous uint8, so the memoryview holds the same bytes `tobytes()` returns, and the pipe write consumes them before returning (an earlier check mode compared a buffer with itself and was removed) | | RoboDojo draft PR #16 (same idea, plus an async writer) |
| `RDTURBO_PCI_COPY=1\|check` | `process_control_info` makes K deepcopies of the control dict; two-level copy + deep-copy of untouched leaves | check: 52,186 pickle-byte comparisons, 0 mismatches | turns itself off when a support robot is present | generic |
| `RDTURBO_BATCH_TENSOR=1\|check` | build joint-target tensors in one `torch.tensor` call instead of three per env | check: 5,174 comparisons, 0 mismatches | falls back row-wise for non-list rows (support arm) | generic |

## Ops (`--profile all`)

| switch | what it does | caveats |
|---|---|---|
| `RDTURBO_NO_PLANNER=1` | do not build the cuRobo planner/IK (only end-effector actions use it); saves ~1.8 GB VRAM per Isaac process | joint actions only; any planner use exits with status 3 |
| `RDTURBO_OFFLINE_ASSETS=1`, `RDTURBO_NV_MIRROR` | alias NVIDIA's S3 host to a verified local mirror of the nine material files every scene fetches (without internet, omni.client's retries hang the first reset for ~120 s and Kit's hang detector kills the run) | a static scan of all assets used by the 54 task configurations (9,570 evaluation layouts) found no other file on that host; do not redistribute the mirror |
| `RDTURBO_SERVER_MEM_FRACTION=<f>` | replaces the Pi_05 server's hard-coded `XLA_PYTHON_CLIENT_MEM_FRACTION=0.3` (unset = upstream) | the override itself was never measured. With preallocation off, XLA's default allocator still caps its pool at this fraction; the speedup preset uses the platform allocator, where the fraction has no effect. Separately, and without any patch, `XLA_PYTHON_CLIENT_PREALLOCATE=false` + `XLA_PYTHON_CLIENT_ALLOCATOR=platform` (set in the speedup preset) made the server use 6.95 GB instead of 10.1 GB (steady state, 0.3 preallocation for the latter) at +2% inference time; an OOM then surfaces mid-run instead of at start-up |

Launcher-side: `RDTURBO_OVERLAP_START=1` starts the clients while the policy server loads (they retry the websocket for
up to 900 s); `JAX_COMPILATION_CACHE_DIR` cut the first inference from 8.4 s to 2.0 s. To attribute a single switch,
compare arms with the same compilation-cache state; the preset-level comparisons (README, docs/benchmark.md) give the
cache to the speedup arm only, because it is part of that preset (about 6 s per run).
